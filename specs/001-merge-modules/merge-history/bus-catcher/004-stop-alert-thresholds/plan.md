# Implementation Plan: Per-Stop Departure Alert Thresholds

**Branch**: `004-stop-alert-thresholds` | **Date**: 2026-09-25 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/004-stop-alert-thresholds/spec.md`

## Summary

Add three configurable, minutes-before-arrival departure thresholds to each
configured stop (heads-up / leave now / missed). Thresholds persist with the
stop config, are validated (non-negative, ordered, defaults 10 / 5 / 1 when
unset), and are served through the existing config API. The SPA's stop card
computes, from each bus's `minutesUntil` and the stop's thresholds, one of four
urgency levels and renders a small colored dot (green / amber / orange / dark
slate-black) on each bus row — no text label, in-app only.

The level is derived purely on the client from data already in the stop-times
response; the backend stores and validates thresholds only.

Both the SPA and the published component get the logic through the same code:
`frontend/src/index.ts` re-exports `StopCard` from the exact file the SPA
dashboard renders, so updating `StopCard` + `StopTimesList` + the shared
`urgency.ts` module covers both consumers with a single shared implementation.
The library's public type surface MUST also export `DepartureThresholds` (and
the `UrgencyLevel` type) so external consumers can type the new prop.

## Technical Context

**Language/Version**: TypeScript 5.7 (workspace `typescript`, Node >= 24, ESM)

**Primary Dependencies**:
- Backend: Hono (HTTP), better-sqlite3, Drizzle ORM 0.45, zod 4
- Frontend: React 19, Vite, Tailwind CSS v4, TanStack Query, Storybook 9,
  Vitest + Testing Library

**Storage**: SQLite (`./data/bus-catcher.db`) via Drizzle ORM;
`configured_stops` table gains three nullable integer columns

**Testing**: Vitest (backend + frontend). Backend config tests use an
in-memory SQLite DB; frontend uses Testing Library + jsdom. Gates:
`pnpm lint`, `pnpm format`, `pnpm test`, `pnpm typecheck`,
`node scripts/scaffold.mjs --check`

**Target Platform**: Node >= 24 (REST service), current evergreen browsers
(SPA), published component library `@sousa99/bus-catcher-components`

**Project Type**: Web application (React SPA + Node REST service, shared JSON
API) with a published frontend component library

**Performance Goals**: Not critical — config operations are single-user and
low-volume; urgency derivation is O(rows) per card with no network impact

**Constraints**:
- Thresholds are plain minutes (no wall-clock / timezone math); level is
  derived from the already-computed `minutesUntil` regardless of live vs
  scheduled source (constitution II unaffected)
- Color-only dot encoding is an accepted tradeoff (no color-blind requirement)
- Thresholds must not change existing add/remove/enable/line-filter behavior

**Scale/Scope**: Single-user home module; a handful of configured stops, ~5
bus rows per stop

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Assessment |
|-----------|------------|
| I. Location-Scoped Data | Pass — thresholds hang off configured stops, which are location-scoped; no context-free queries |
| II. Freshness-Aware Realtime | Pass — thresholds do not alter staleness logic; level uses `minutesUntil` from live or scheduled data, and the realtime notice is unchanged |
| III. Provider Abstraction | Pass — no provider change; config is local DB only |
| IV. Test-First (NON-NEGOTIABLE) | **Gate** — new logic (backend threshold validation + defaults resolution, frontend urgency-level + dot mapping) MUST have tests written and confirmed failing before implementation (Red-Green-Refactor) |
| V. Observability & Correct Time | Pass — no new time handling; thresholds are plain integers; config mutations keep existing structured-logging behavior |

Data & Integration: threshold values validated via zod schemas on create and
update; malformed/out-of-order values rejected with `invalid_body` (never a
crash). Quality gates all apply.
